# ADR-006: `ERR-08` 改为宽限跳过语义（未配置 Key 不算失败）

- **状态**: 已接受 (Accepted)
- **日期**: 2026-09-24
- **关联**: `03` §2.2 / §4、`04` §2、`00` §3、`05` §2.2

## 背景

`v0.1.1` 起 Jev 接入采用 BYOK（`00` §5），`03` 原行 `ERR-08` 为 ERROR 级「提示一次并终止」。存量 `v0.1.0` 用户升级后**必然未配置 Key**：按原语义，升级当天功能即不可用，且必须先完成 Key 配置才能恢复——升级即破坏。

## 决策

`ERR-08`（API Key 未配置）由「ERROR，提示一次并终止」改为 **WARN 宽限跳过**：

- 检查**静默跳过**（视为零风险放行，不进错误态、不弹清单、不算失败）；
- **首次**遇到未配置 Key：一次性通知「SoneCheck 需要 Jev API Key」，带「设置 Key」按钮直达 `sonecheck.setApiKey`（`API-03`）；
- **后续**检查：仅状态栏短暂提示 `SoneCheck: 未配置 Key`（2s，与其他瞬时态一致）。

## 原因

1. **升级零破坏**：宽限语义让 `0.1.0 → 0.1.1` 的升级对未配 Key 用户无感，配置引导与功能可用解耦。
2. **`INV-01` 的自然延伸**：「任何失败都必须以放行收尾」——缺配置是一种可自愈的未就绪态，不是需要终止的故障。
3. **`US-03` 零打扰**：一次性引导 + 后续状态栏瞬时提示，不形成循环打扰。

## 后果

✅ 升级路径无破坏；引导可达（按钮直达 `API-03`），且不循环打扰
⚠️ 「为什么没清单」的 discoverability 依赖那一次引导通知；用户错过引导后只能靠状态栏瞬时提示 + 文档
🔧 `03` §2.2 / §4 的 `ERR-08` 行（级别 ERROR → WARN）与生效版本段须同步；属**契约语义变更**，按 `03` §5 走本 ADR 登记
🔧 `04` §2 状态表须补「未配置 Key」态

## 替代方案

| 方案 | 否决原因 |
|---|---|
| 维持 ERROR「提示一次并终止」 | 升级即破坏存量用户体验；「先配 Key 才能用」与可分发目标（US-04）相悖 |
| 每次检查都弹引导通知 | 打扰严重，与 US-03 零打扰直接冲突 |
| 完全静默（仅状态栏闪一下） | discoverability 最差，用户无从得知需要配 Key |
