## 1. 业务背景与问题定义

AI 编程工具（Copilot / Claude Code / Cursor 等）让代码**产出速度**远超人工**审阅速度**：一次提交动辄几十个代码块、横跨多个文件，人类无法逐行读完；Code Review 因此积压，低质量改动常被「习惯性放行」。

现有「生成式 AI 审查」方案存在三个结构性问题：

| 问题 | 表现 |
|------|------|
| 慢 | 一次审查需数秒级（公开宣传口径为 5–15s，非本项目实测），破坏提交心流，用户直接跳过 |
| 贵 | 按生成 token 计费，全量 diff 扫描成本难以承受 |
| 幻觉 | 会生成解释甚至改写建议，产生假代码与错漏 |

sonecheck 的切入点是**替换掉审查链路中「生成」这一环**：用 Jev（System-1 决策模型，只输出结构化 `choice` / `score` / `noul` 三类原语，不生成文本）把 diff 切成块并在**亚秒级内**完成打分，只把最值得人看的那 1–3 块推到眼前。

- **一句话定位**：Sub-second System-1 AI code risk inspector for VS Code and Git hooks —— 在提交前把「最值得你亲自看的那几行改动」挑出来。
- **核心价值主张**：与生成式 AI 审查相比，快一个数量级以上（亚秒级 vs 数秒）、零幻觉（只打分不生成代码）、成本极低（输出免费）、低打扰（无风险时完全静默）。
- **命名规范**：仓库名 / npm 包名 / CLI 命令统一用全小写 `sonecheck`；品牌展示与 VS Code 插件显示名用 `SoneCheck`。

> **免责声明**：`Jev` 与 `TypeSafe AI` 为其各自所有者的商标或产品名。sonecheck 是独立的**非官方**项目，与上述主体不存在隶属、赞助或背书关系；本文档引用这些名称仅为说明技术依赖。

## 2. 核心用户故事 (User Stories)

| 编号 | 角色 | 期望 | 价值 |
|------|------|------|------|
| US-01 | 个人开发者 | 我希望提交前插件自动扫描暂存区改动并按风险排序 | 以便不必逐行读完整份 diff |
| US-02 | 个人开发者 | 我希望点击风险条目直接跳到对应代码行 | 以便快速确认，不必手动检索 |
| US-03 | 个人开发者 | 我希望没有风险时完全不被弹窗打扰 | 以便保持提交心流不被打断 |
| US-04 | 隐私敏感的企业开发者 | 我希望只有改动块与局部上下文离开本机 | 以便通过公司安全审查 |
| US-05 | Tech Lead | 我希望团队统一风险规则并留审计痕迹 | 以便鉴权 / 支付等关键路径必经人工确认 |

## 3. 非功能性需求 (NFR)

| 维度 | 要求 | 验收方式 |
|------|------|----------|
| 性能 | 单次检查端到端 p95 ≤ 1s；单块判定 ≤ 500ms；检查全程后台异步，不阻塞编辑器输入 | 真机计时（结构化日志落地后补自动 Elapsed 留痕） |
| 安全 | API Key 仅存 VS Code SecretStorage；**绝不上传全量源文件**；日志与遥测禁止出现 Key 及源码明文 | 代码审查 + 关键路径断言（出站内容不含全量源文件 / 日志不含 Key 与源码明文） |
| 可用性 | Jev 不可用 / 超时 / 配额耗尽时降级为静默放行 + 一次性提示，**绝不阻断提交** | 断网与错误注入测试 |
| 兼容性 | VS Code 稳定版（最低 `^1.90.0`）；Node 22 运行时；macOS / Windows / Linux | 真机 + CI 矩阵 |

> **数值口径**：本表具体数值均为**本项目自设的验收线**，不引用任何第三方厂商的宣传指标；实测回填前不得对外作为承诺。对外文案统一使用定性量级（如「亚秒级」）。
> **数值层级（禁止倒挂）**：端到端预算（p95 ≤ 1s）⊃ 单块判定（≤ 500ms）⊃ 单请求超时上限；任一层设定不得突破上一层预算。

## 4. 业务验收标准

- [ ] 在真实仓库的一次 ≥10 块改动提交中，插件 1s 内输出风险清单
- [ ] 全部为低风险改动时，除一次状态提示外零弹窗（零打扰）
- [ ] 从清单点击条目到光标定位目标行的成功率 100%（真机验证）
- [ ] 断网状态下提交流程完全不受影响
- [ ] 打包 `.vsix` 可在干净 VS Code 上 `Install from VSIX` 并跑通完整链路
- [ ] npm 上 `sonecheck` 可被 `npm view sonecheck` 查询到（**已达成**：`0.0.1` / `0.0.3` / `0.0.4` 已发布）

## 5. 边界与非目标

| 明确不做 | 原因 |
|----------|------|
| Webview 侧边栏 | 样式调试耗时会吞掉 MVP 时间窗 |
| 完整 AST 语义分析 | 先用「diff hunk + 上下文行」验证价值，再决定是否升级 |
| Git Hook 强制拦截 | 强制拦截的误报代价极高；v0.1.0 仅手动触发 |
| 服务端 Proxy / 托管 API Key | 避免过早承担运营成本与数据合规责任 |
| 自动改写代码 | Jev 不生成内容；任何修复动作由用户或后续版本承担 |
| 多语言 AST / 多模型路由 | 单点价值验证后再扩展 |

> **关于定位中的「and Git hooks」**：指**后续版本**的**非强制**集成——在 `pre-commit` 等钩子中触发检查、结果只提示不阻断；**强制拦截**明确不做（见上表）。`v0.1.0` 仅提供命令面板手动触发。
